## 3. 根因

`run_pipeline.py` Step 8 有兩種輸出：

- 影片模式（手動跑）：`output/<slug>/剪輯後.mp4`
- 音訊模式（worker 一律 `--skip-cut`，來源是 mp3）：`output/<slug>/音訊.mp3`

2026-11-02 為了避免「音訊被誤命名成 剪輯後.mp4」，Step 8 改成兩分支，但**收尾的 `print` 還寫死 `final_video.name`**：

```python
    if src_suffix in (".mp3", ...):
        final_audio = output / "音訊.mp3"
        shutil.copy2(src_video, final_audio)
        ...
    else:
        final_video = output / "剪輯後.mp4"
        ...
    ...
    print(f"  影片：{final_video.name}")   # ← 音訊模式沒有 final_video
```

→ 只有「worker 跑影片任務」會踩到；手動跑 `python run_pipeline.py xxx.mp4` 不會。這也是為什麼
之前 1913／1918／1919 那一輪（10-28 林昇直播）會反覆失敗、重跑、甚至產生 1918／1919 重複任務，
看起來像「這支影片又出問題」，其實是同一個收尾 bug 還沒被發現。

### 為什麼會變 8 次全長 pipeline

`worker.process_video_task()` 失敗後會把任務改回 pending 並遞增 `retry_count`（上限 3），
而 pipeline **沒有續傳機制**，每次都從「壓縮→轉錄」重來。所以一次收尾 bug = 4 次全長重跑；
1921／1923 兩支重複任務 = 8 次。這是這次時間與額度被吃掉的真正來源。

## 5. 為什麼「153/200（76%）」還會爆額度？

### 結論

**因為「200 次／5 小時」這個模型本來就不是伺服器現在的規則**，76% 是假的安心感。

### 事實（本次可驗證）

- 21:31:52 被拒當下，本機 DB 統計：
  - 最近 5 小時免費請求：**153 次**
  - 當天（台灣時間）免費請求：**337 次**
  - 當天全部免費請求都是 `opencode/big-pickle`
- 日誌原文：
  `level=ERROR ... AI.Error: Free usage limit reached. Free models work in OpenCode; subscribe to OpenCode Go...`
- 歷史撞牆點（同一支工具算出來的「5h 次數」）：**225、233、205、153** —— 根本不是固定的 200。

### 伺服器實際規則（2026-10-23 起）

- 免費額度是「**每個 IP × 每個 UTC 日**」的 bucket，**UTC 00:00 = 台灣 08:00 換日**。
- 上限**動態調整、不公告**（OpenCode 維護者公開回覆：依容量與需求調整，且是「帳號／網路整體」共用）。
  社群實測第一次被拒的點：**168 次、215 次**，也有人當天跑到 900 多次才被拒。
- UI／API 都沒有剩餘量可查；只有 Go 有官方 `/inference/go/v1/usage`。
- 被拒的請求不計入用量，所以「重試」不會救回額度。

### 這次實際發生的事

1. 這個對話一開始跑在**免費模型 `opencode/big-pickle`**（21:25 起）。
2. 單一個回合做了大量工具呼叫（讀檔、跑 python、查 DB、查日誌…），**6 分鐘 84 次請求**。
3. 當天早些時候（11:44–18:39）另一個 session 已用掉 253 次，UTC 日累計到 **337 次** → 撞上當天的動態上限。
4. 21:33 之後切到 `opencode-go/deepseek-v4.1-flash` 才恢復（Go 月額度官方顯示 100% `rate-limited`，
   但實測請求仍可成功，屬超額狀態）。

### 之後怎麼判斷（新規則）

- `python oc_usage.py` 會顯示：`免費 UTC日 337 次（08:00 換日）｜5h 參考 153`。
- **看到 UTC 日累計 ≥150 就當「隨時會斷」**；≥200 幾乎可以直接視為已用完（除非當天伺服器放寬）。
- 長任務（批次修檔、逐字稿、多工具 agent）**先切 `opencode-go/*` 再開工**；免費池只做短、可丟棄的事。

> 補充：本次「免費池燒光」不是 worker／Groq／Gemini 造成，是 **agent 對話本身**在免費模型上跑太重的調查
> （大量工具呼叫）所致。Groq（轉錄）與 Gemini（筆記／摘要）走的是各自的 key，與 OpenCode 免費池無關。

## 8. 這次學到的三件事

1. **「看起來成功」不等於完成**：字幕、音訊、metadata 都寫好了，卻死在最後一行 `print`；
   驗收看的是「任務狀態＋KB 檔案」，不是 output 有沒有檔案。
2. **重試必須便宜**：沒有續傳的重試＝重複燒轉錄與 CPU。`--resume` 是這類 bug 的止血帶。
3. **額度顯示要看對模型**：免費池是「UTC 日動態總量」，不是「5 小時 200 次」；
   會花掉它的是 agent 的工具呼叫回合數，不是 worker 的影片流程。
