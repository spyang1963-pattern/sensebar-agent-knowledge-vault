# 知識庫影片位置「單一權威」處理記錄（2026-11-12）

## 一、使用者要求

1. 每一篇影音條目（逐字稿／摘要／課程筆記）都要**自動**標明影片在哪一台機器、哪個路徑，
   而且要能一鍵點播，不再逐案補、不再需要猜。
2. 「從出生就帶連結」要真的成立：誕生、打包、收割各階段都自動接上。
3. 非本機（PC1／PC2／PC3 收割來的）條目，在 notebook 也要看得出對應哪一台的影片。
4. **備份檔的知識庫不要再處理**，只把「現在的知識庫」做好。
5. 查不到來源機就明確標「未確認」並列報告，**不要猜**。
6. 保留影片所在位置路徑與原始 YouTube 網址。

## 二、根因矩陣（為什麼以前一定漏）

| # | 產生者 | 寫出的格式 | 舊補救腳本認得嗎 |
|---|---|---|---|
| 1 | `channel_watcher.create_kb_entry()` | `- 本機影片：D:\…`（無機器名、無連結） | 部分 |
| 2 | `run_pipeline.py` + `scheduler.harvest()` | `## 影片` 下一行**裸路徑** | **不認得** |
| 3 | `publish_outbox.rewrite_producer_paths()` | `- 燒字幕影片（在 PC2）：[▶ 點播](file://…)｜\\ip\…` | 認得 |
| 4 | `backfill_video_links.py`／手動 | `- 本機影片：[▶ 點播](file:///D:/…)｜D:\…` | 部分 |

`fix_video_links.py` 只處理第 3、4 種（且只換 `.lnk`，不補機器名）；第 1、2 種永遠補不到。
新條目只要走不同路徑（本機 `video` 任務 vs PC 的 YouTube 任務），就會出現「有的可點、有的要猜」。

實際案例：

- `knowledge-base\CMoney_直播\2026-11-11_權證小哥-…md`：PC1 產出，`## 影片` 裸路徑
  `D:\CMoney_直播\…`，收割後 notebook 直接留下 PC1 的本機路徑（看起來像 notebook 的檔案）。
- `knowledge-base\XQ直播_Videos\2026-11-11-XQ-微風療養院長-…md`：notebook 本機 `video` 任務，
  `## 影片` 裸路徑，沒有機器名也沒有可點連結。
- `20VTA 頻道\直播\2026-11-09_…md`：唯一正確樣板（PC2 + UNC + `.lnk`）。

## 三、設計：`video_links.py` 是唯一出口

```
誕生  channel_watcher.create_kb_entry ─┐
收成  scheduler.harvest ───────────────┤
產品  worker.process_note/summary ─────┼→ video_links.normalize_file()
打包  publish_outbox ──────────────────┼→ video_links.pack_text()
收割  harvest_daily.bat ───────────────┼→ python -X utf8 video_links.py
補救  fix_video_links.py（shim）───────┘
```

### 標準行

```
- 本機影片（在 notebook）：[▶ 點播](file:///…/_video_links/<id>_video.lnk)｜D:\XQ直播_Videos\…
- 燒字幕影片（在 PC2）：[▶ 點播](file:///…/_video_links/<id>_burned.lnk)｜\\100.113.234.81\YouTube_Videos\…
```

產品（` 摘要.md`／` 課程筆記.md`）：

```
> 影片位置：（在 notebook）[▶ 點播](file:///…/_video_links/<id>_video.lnk)｜D:\…
```

### 機器判定順序（不猜）

1. 絕對路徑且**本機存在** → 本機（`config.MACHINE`）
2. UNC → 用 `config.TAILSCALE_IPS` 反查機器
3. 歷史條目 → `working/harvest_ledger.json` 的收割帳本回推來源機
4. 都沒有才探測各機 SMB 分享（`--no-probe` 可關）
5. 仍未知 → `（在 未確認）`＋保留原路徑，列進 `working\video_links_report.txt`

### 其他規則

- 遠端影片 `D:\<root>\…` → `\\<該機 IP>\<root>\…`，**該分享真的存在才用**；
  沒開分享 → 保留機器名＋原路徑（誠實），列報告的「no-share」區。
- `## 影片` 的裸路徑一律轉成標準行；GUI 改用 `video_links.first_video_path()` 解析。
- **備份／內部目錄不處理**：`_harvest_overwritten`、`_harvest_conflicts`、
  `_archive_no_transcript`、`_video_links`、任何 `backup_*`。
- `.lnk` 命名沿用舊規則（`<video_id>_video/_burned.lnk`；無 id 用 `sha1(目標)[:12]`），
  同名不同目標補 `sha1[:6]` 消歧；一次 PowerShell 只建 300 個（避免 1000+ 逾時）。
- 冪等：第二次跑「需改寫 0」；`.lnk` 目標沒變就不重建（`_video_links\_targets.json`）。

## 九、`.lnk` 產生器的兩個坑（2026-11-12 實踩，勿改回）

### 坑 1：`WScript.Shell` 只吃系統 ANSI 碼頁（本機 Big5/cp950）

第一版用 `$ws = New-Object -ComObject WScript.Shell; $s.TargetPath = ...; $s.Save()`。
PC1 收割來的檔名含**簡體專用字**（`恶` U+6076、`学` U+5B66、`众` U+4F17），
Big5 組不出來 → `TargetPath` 丟 `ArgumentException（值未落在預期的範圍內）`，
**但 `Save()` 仍留下 80 bytes 的空殼 `.lnk`**，而且腳本沒檢查、看起來像成功。
實測（`[System.Text.Encoding]::Default.WebName` = `big5`）：

| 字 | 結果 |
|---|---|
| `恶`(U+6076)、`学`(U+5B66)、`众`(U+4F17) | ✗ E_INVALIDARG |
| `惡`(U+60E1)、`學`(U+5B78)、`眾`(U+773E)、`网`、`里` | ✓ |

代價：205 個 `.lnk` 是空殼，條目點擊完全沒反應（`_targets.json` 記的目標卻正確，所以更難發現）。

**解法**：改用 `IShellLinkW`（UTF-16）直接寫，與檔名用哪種中文無關。
`video_links.py` 的 `LNK_CS`／`LnkWriter.Make` 就是這個（C# `Add-Type` + `IShellLinkW`/`IPersistFile`）。

### 坑 2：`IPersistFile::Save` 只吃絕對路徑

同一段程式一開始每個目標都回 `E_INVALIDARG`（`0x80070057`），連純 ASCII 也失敗，
`SetPath` 卻完全正常 —— 因為 `Save()` 收到的是**相對路徑**（`working\_vl_lnk_test3`）。
`LnkWriter.Make` 現在先 `System.IO.Path.GetFullPath(outDir)`；Python 端 `make_shortcuts()`
也先 `.absolute()`。**兩邊都要，少一邊就會再炸**。

### 空殼偵測（防止再次無聲失敗）

- `lnk_ok(path)` = 檔案存在且 `size >= 200`（正常 `.lnk` 300~2300 bytes；空殼固定 80 bytes）。
  `_write_links()` 用它判斷要不要重建，所以空殼會**自動**被重寫。
- `python -X utf8 video_links.py --verify`：用 `LnkWriter.Get()` 回讀全部 `.lnk`，
  與 `_targets.json` 比對（`\..\` 會正規化，用 `ntpath.normpath` 比），
  有任何空殼／缺檔／目標不符就 `rc=1` 並列報告。改動 `.lnk` 相關程式碼後**必跑**。

### 另一個副作用：`WScript.Shell` 會偷改字元

Big5 可表示但「一碼多字」的字會被換掉：`•`(U+2022) → `‧`(U+2027)
（兩者在 cp950 都是 `A150`）。7 個舊 `.lnk` 因此指向不存在的 `‧` 檔名。
`--force` 全部重建後已歸零；`IShellLinkW` 實測原樣保留（`bullet_video.lnk` 內仍是 U+2022）。
